# 人物与物品批量制作参考

整理日期：2026-10-18。基于本仓库的人物、家具、动态素材页与导出流程。

核心经验：先固定骨架、尺度、坐标和交互规则，再批量变化外观；每件素材都应能独立预览、进入真实场景，并追溯到生成它的数据。

## 1. 批量制作前先明确交付物

本项目运行时用 JavaScript 生成人物和家具。图片可以作为设计参考，PNG 和 GLB 可以作为导出产物，但单独生成一张图片不会自动得到可旋转、可做动作的角色。

| 交付物 | 当前用途与边界 |
| --- | --- |
| 人物身份与外观数据 | 身份在 `characters`，外观在 `appearances`；共享模型解释这些参数 |
| 人物模型与动作实现 | `model.js` 和 `appearance.js`；发型、服装等新类型需要实际实现 |
| 家具构建器与规格 | 构建可摆放的模型；按用途提供尺寸、碰撞、座位或显示器挂点 |
| 素材预览定义 | 提供独立预览所需的名称、分类和构造参数，不决定办公室摆放 |
| 人物 PNG/GLB | 头像、对照图及静态模型快照；当前 GLB 不包含 JavaScript 动作和表情逻辑 |

批次开始时写清需要哪些交付物，例如“新增 20 个可工作的人物”或“新增 10 件可独立摆放的家具”，再定义验收项。

## 2. 人物：统一骨架，允许体型差异

### 保持稳定的部分

- 沿用相同的关节层级、身体朝向和动作接口，让现有动作能复用。
- 根节点负责场景摆放，身体节点负责体型变化；不要为了让预览图看起来一样大，修改人物的真实尺度。
- `height` 是纵向缩放系数，`build` 是横向与前后方向的缩放系数，均不是以米计的实际身高。
- 地面、座位锚点和工作姿态的骨盆基准需要分清。当前工作姿态补偿了骨盆高度，仍没有自动把手脚对齐家具的完整能力。
- 头发、帽子、围巾、裙摆应挂在适当的身体或关节节点上，并随动作检查。

### 逐步变化的部分

第一批样件可先固定 `height: 1`、`build: 1`，验证共同的桌椅和动作；再加入高矮、胖瘦差异。配色、发型、服装、配饰和五官可以组合变化，但只填写构建器已支持的类型。新增一个类型名称，不会自动生成对应造型。

例如阿远 `team-05` 的身高系数为 1.09，阿墨 `team-07` 为 1.01，纵向缩放相差约 8%。这种差异可以保留；实际包围盒还受发型、帽子和姿态影响，不能只比较 `height` 数值。

验收关注真实接触关系：坐下后身体与椅子是否合理、手是否靠近键盘、脚是否悬空或穿地、头部和配饰是否挡住显示器。不要把某次通过的系数范围视为所有新服装、新家具都适用的安全范围。

## 3. 物品：先约定尺寸、原点与用途

每类物品建立一个基准样件，用它校准后续变体。

| 约定 | 制作要求 |
| --- | --- |
| 尺度 | 在同一世界单位中，与现有桌椅、人物、杯子对照；不要逐件按预览画面归一化真实尺寸 |
| 原点与朝向 | 明确底部、中心或挂点作为构造基准，以及正面方向；与同类构建器保持一致 |
| 放置规则 | 区分落地、桌面和挂墙物品；桌面物品接收桌面高度，不写死房间坐标 |
| 交互挂点 | 椅子提供座位，显示器提供真实屏幕和正面挂点，组合工位从同一座位契约派生位置 |
| 碰撞 | 导航预留范围与可见模型分别定义，并验证两者关系；装饰物按用途决定是否阻挡通行 |
| 变体 | 颜色、宽度、支架等差异优先参数化；形态或交互接口明显变化时再建立新素材 ID |

家具构建器只读取传入的实例和参数，不导入具体布局，不读取页面控件。同一件桌子应能在不同办公室中移动、旋转和复用。

预览页会为物品居中并调整取景，因此“在预览里看起来大小合适”不能证明原点和真实尺寸正确，仍需在同一场景中与基准物品对照。

## 4. 身份、外观、实例和业务绑定分开管理

| 标识 | 表示什么 | 批量制作规则 |
| --- | --- | --- |
| `characterId` | 人物身份 | 改名或换衣服不改变身份 ID |
| `appearanceId` | 一套外观 | 同一人物可以有多套外观，保留各自稳定 ID |
| `instanceId` | 场景中的一次出现 | 相同人物进入不同场景时使用不同实例 ID |
| `agentId` | 业务 Agent | 由业务显式绑定，不用人物姓名或外观 ID 代替 |
| 物品 `assetId` | 可复用物品类型或变体 | 与摆放实例的 `id` 区分，避免重排后失去绑定 |

已有的 `team-05` 等外观 ID 是历史稳定标识，不应因换办公室或列表排序而改名。新 ID 应提前分配，避免生成时按当前数组下标重新编号。

建议每批保留一份制作清单，记录 ID、名称、参考图或设计说明、参数、版本、制作状态、验收结果及产物位置。这是建议的制作记录；当前没有通用的 CSV/JSON 批量导入接口。

## 5. 按“样件—组合—批量—发布”的顺序推进

1. **定义批次规格。** 确定数量、风格、支持的类型、尺度基准、所需交互和输出格式。
2. **制作 3～5 个代表样件。** 人物覆盖高矮、宽窄及较复杂的服装配饰；物品覆盖不同尺寸与摆放方式。确认共同规范后再扩量。
3. **验收独立预览。** 检查正侧背视图、底部、尺寸、朝向和 ID。人物检查全部动作和表情，尤其是工作、行走和庆祝时的穿插。
4. **验收真实组合。** 人物与桌椅键盘一起检查；物品测试移动、旋转、重排和不同布局。极端样件优先验收，失败时先修规则或构建器。
5. **批量生成并逐项登记结果。** 将未制作、待验收、通过、失败分开记录。超时和生成失败不能算通过，重跑时保留已通过项。
6. **验证后发布。** 核对源码、预览、场景和导出清单是否一致，再构建或导出；保留可恢复的旧产物。

当前有 6 种动作、4 种表情。对于新增服装或特殊人物，建议验收 24 种动作与表情组合，并覆盖多个时间点；现有素材页自动检查会逐个切换动作、表情，但没有穷举全部组合和每一帧的接触关系。

## 6. 分别验收目录发现、场景使用和导出

### 人物接入

当前完整使用链路以 `src/assets/characters/catalog.js` 为人物目录：在 `characters` 中登记身份，在 `appearances` 中登记外观及 `characterId`。需要进入办公室时，再通过布局人物引用与 `instantiateCharacter()` 创建场景实例。

人物预览页还能发现子目录中的 `catalog.js`，但当前实例化和导出工具直接读取主目录。若批量制作时按子目录分组，必须先把主目录改为统一聚合入口并验证整条链路，不能仅凭“预览页出现了”判断已完成接入。当前优先使用主目录登记。

新增发型、服装、配饰或表情时，应同时检查 3D 实现、头像绘制和相关目录元数据；新增需要导出的外观字段，还应检查 `src/tools/character-roster.js` 的 `LOOK_KEYS`。仅在配置中增加字段，可能不会进入导出或变更检测。

### 物品接入

在 `src/assets/furniture/` 中提供构建器，并添加导出 `assetPreviews` 的 `*.preview.js` 文件，预览页会自动发现。实际用于场景时，还要接入对应的组装或家具注册入口；当前工位注册表具有工位专用契约，普通杯子、柜子等不能只登记一个 ID 就按工位组装。

写在 `environments/` 房间构建器内部的柜子、沙发等，如果需要成为可批量复用的物品，应先提取为独立构建器。

现有两页适合检查单件素材，尚无批量尺寸对照视图、自动家具适配或物品通用批量导出工具。开发服务器会随目录变化更新，生产版本需要重新构建。

## 7. 安全导出与资源管理

人物导出需要先启动开发服务：

```powershell
npm run dev
# 在另一个终端执行；新增人物或外观集合时完整导出。
npm run export:characters

# 已有完整且有效的产物集时，仅更新指定外观的全部三类文件。
npm run export:characters -- --ids=team-05

# 外观未变化，只需要重做头像时，可以进一步限制种类。
npm run export:characters -- --only=portrait --ids=team-05
```

新增或删除外观集合时进行完整导出。已有外观变化时，为受影响的外观重新生成全部三类产物；不要只更新头像，留下旧模型和旧对照图。不要手动清空导出目录，沿用临时目录生成、格式与哈希校验、失败回滚的发布流程。

人物 GLB 当前是静态快照。若需要在其他引擎播放动作、动态表情或批量导出物品，需要另行实现相应的动画、纹理或导出管线。

自定义预览和批量生成器必须持有共享美术资源租约。处理完一件素材后释放私有资源，全部处理结束后释放租约；共享缓存不能被单件任务提前销毁。控制 WebGL 上下文数量，批量缩略图复用渲染器，避免每个列表卡片各开一个上下文。

## 8. 发布前的最小验收清单

- ID 唯一，人物身份与外观绑定正确；不依赖姓名或数组顺序查找素材。
- 构建器支持所有参数值，头像、3D 外观和导出清单一致。
- 同一尺度下尺寸合理，原点、朝向和挂点明确，能正确移动与旋转。
- 人物动作和表情正常，极端体型与复杂服饰完成家具接触检查。
- 物品进入真实场景后，显示、碰撞和业务挂点保持一致。
- 预览能反复切换、卸载和重新挂载，失败任务不破坏其他素材或共享资源。
- `npm test`、`npm run build`、`npm run test:browser:assets` 通过；修改场景后执行仓库要求的引擎、资源、家具、组合、任务与工位几何检查。
- 导出经过格式、大小和哈希校验；失败、超时与未覆盖项目单独记录。

以上清单包含制作建议，不能据此认为现有测试已覆盖所有接触关系。后续扩量时，优先补充批次参数校验、同尺度对照视图和极端样件的组合验收，再引入自动贴合家具的能力。
