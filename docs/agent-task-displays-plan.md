# 多 Agent 动态任务显示实施计划

本文件为原始实施计划。2026-10-16 已按后续执行请求完成实现，结果见 [实现与验收记录](./agent-task-displays-validation.md)。范围限定为 `example/office-voxel/`，沿用现有 Three.js、原生 JavaScript、Vite 和像素场景。

后续更新：五种布局现已迁移到统一场景引擎，当前模块边界见 [共享场景引擎](./shared-scene-engine.md)。下文入口现状记录的是任务显示功能实施前的状态。

## 1. 目标与范围

把现有装饰性的黑板、白板和电脑显示器变成多 Agent 任务的实时显示终端。

- 主任务板：任务主题、简短目标、任务状态、已完成子任务数。
- 分块白板：每块显示一个子任务的标题、内容摘要、负责人和状态；不能只画状态色块。
- 工位电脑：显示对应 Agent 的当前子任务、当前操作、公开运行日志/工具结果摘要及最终输出摘要。
- 所有显示来自同一份运行状态；先通过本地 mock 事件流驱动，保留后端数据源替换接口。
- 新增“任务主题”“子任务看板”“返回全景”按钮；点击现有人物头像打开菜单，再点击“查看电脑屏幕”聚焦该人物的工位显示器。
- 保留现有房间构图、人物外形、家具风格和动作操作。只调整承担信息显示的面板，必要时扩大或新增。
- 默认覆盖五种布局：三人 `index.html`、九人 `nine.html`、`loft.html`、`suite.html`、`floor.html`。先完成 Loft 的垂直流程，再适配其余布局；仅完成 Loft 不算本任务完成。
- 不实现真实后端服务、真实远程桌面/终端视频流、Agent 调度器或模型内部推理展示。本期“运行时显示”指可观察的运行事件与输出。

## 3. 交互与显示规则

### 主任务板

保持黑板/深色屏的物理质感，突出中文任务主题，下面放一到两行目标、状态及完成数。主题在一次运行期间保持稳定，状态和完成数随事件更新；重播清空上一轮状态。

### 子任务看板

使用白板分格，每格为“标题 + 简短内容 + 负责人 + 状态”。状态至少包含等待、运行中、受阻、完成、失败。状态文字和标记同时出现，不能仅靠颜色辨别。

根据面板实际尺寸决定一页可显示的卡片数。超出容量分页；聚焦后提供上一页/下一页及页码，未聚焦时可缓慢轮播，聚焦阅读时暂停自动翻页。长文本按中文及中英文混排换行，超长正文分页，标题在模型尺寸允许范围内扩行；不要无限缩小字体。

多房间布局的房间白板显示该房间绑定 Agent 的子任务；公共看板提供整个任务的总览。“子任务看板”按钮默认聚焦总览，多块看板时提供明确的房间/看板选择。主任务主题需在可见公共位置提供，不允许只藏在某间房间中。

### 电脑

每个人物拥有稳定的 Agent 绑定和工位绑定，即使人物走动，菜单也聚焦其固定电脑。电脑显示 Agent 名称、当前任务/步骤、最近数行输出、运行状态及光标。未分配任务时显示待命，不能串用其他 Agent 的日志。

每台电脑最多保留固定数量日志，例如 200 条；屏幕仅绘制最近能容纳的行。聚焦状态可翻看旧输出并返回最新输出。大段代码或工具结果显示摘要，不把整份内容缩成不可辨认的小字。

### 入口与镜头

- 工具栏：任务主题 / 子任务看板 / 返回全景。
- 人物头像：点击选中人物并打开菜单，显示姓名、Agent 状态、“查看电脑屏幕”；选择同一头像可收起菜单。
- 菜单支持键盘、Escape、点击外部关闭；不触发底下的地面移动。小屏不越界。
- 镜头朝向显示面的正面，平滑移动并自适应缩放，保证正文可读。保留拖拽中断镜头过渡的能力，减少动态效果模式下直接到位。
- 处理椅子、人物头部和隔墙遮挡，优先使用合适的面板位置/镜头位置。确需局部隐藏时使用可恢复的特写遮挡处理，并考虑家具已合批的事实；不直接修改全局共享材质。
- 退出特写恢复镜头限制与临时可见性状态。“返回全景”恢复既有 room 预设。
- embed 模式仍提供必要的紧凑入口，保留现有嵌入命令兼容性与来源校验。

## 4. 视觉约束

复用 `src/art.js` 和 `src/tokens.css` 的木色、纸白、墨绿、橙色、灰蓝：`#c9a477`、`#f8f9f5`、`#293635`、`#d57645`、`#708fa5`，状态绿沿用 `#79917a`。

显示面的标题、正文、日志及新增菜单采用本地中文像素字体，英文日志优先使用该字体或匹配的像素等宽字体。实施时核验字体来源、许可证、中文覆盖范围和发布体积，保留许可说明。不得以系统中文字体悄悄回退冒充像素字体，也不以强制全英文回避中文需求。

Canvas 使用整数布局、适合字体网格的字号及 NearestFilter；字体加载完成后再绘制，并在加载成功/失败时提供明确处理。`imageSmoothingEnabled=false` 本身不会把普通文字变成像素字。

依据面板比例提高纹理尺寸，例如电脑从现有 64×40 提升到约 384×216 或相近比例，白板按可显示行数确定。最终分辨率以中文可读性与 Floor 的 24 台电脑表现为准。禁用不必要的 mipmap，内容变化才重绘；光标低频更新，不能每帧重画所有屏幕。

## 5. 数据模型与动态 mock

建议建立独立于 Three.js、DOM 的运行状态模块，以 JSDoc 明确类型。

```text
Run: id, title, objective, status, startedAt, updatedAt
Subtask: id, runId, title, description, assigneeAgentId,
         dependsOn[], status, summary
Agent: id, name, status, currentSubtaskId, currentStep
LogEntry: id, agentId, subtaskId, timestamp, kind, text
Binding: agentId, actorId, stationId, displayId, roomId?
Event: runId, seq, type, payload
```

`actorId` / `stationId` 必须稳定；不得用姓名作为主键，也不得默认 Agent 数组顺序等于人物或电脑数组顺序。依赖现有 `stationFor` 完成显式映射。任务进度优先从已完成子任务数推导，避免随机生成无来源百分比。

统一事件例如 `run.started`、`subtask.created`、`subtask.updated`、`agent.updated`、`agent.output`、`run.completed`。定义完整快照初始化、订阅、退订/销毁接口；所有事件先更新状态，再通知显示控制器。最小校验覆盖运行 ID、序号、实体引用和日志长度；同轮重复/旧事件不重复追加。真实网络重连协议留待后端接入时实现。

Mock 示例主题：“为像素办公室实现多 Agent 任务展示”。脚本依次模拟需求梳理、界面设计、数据协议、场景接入、验证与汇总，包含至少两个 Agent 并行输出、一个受阻后恢复的过程和最终完成。

- 使用确定性的事件时间轴，运行约 60–90 秒；不同 Agent 输出各自相关的日志。
- 三人布局可让同一 Agent 依次处理多个子任务；九人和 24 人布局采用对应数量的绑定，多余 Agent 合理待命。
- 提供“暂停演示 / 继续演示 / 重新演示”，并标注模拟数据。
- 演示时钟与现有“暂停动画”明确区分；暂停演示冻结数据事件和输出，镜头与菜单继续可用。
- 完成后保留最终结果，手动重播，不强制自动清空。
- 测试可注入时钟或指定时间点，不依赖长时间真实等待。

## 6. 推荐模块与接入边界

在 `src/shared/` 下新增功能模块，名称可按实现微调：

- `task-runtime.js`：状态、事件应用、订阅、校验和日志容量。
- `mock-task-source.js`：确定性场景脚本、演示时钟、暂停/继续/重播。
- `display-surface.js`：Canvas、纹理、材质、重绘与资源生命周期。
- `task-display-renderers.js`：主题板、子任务卡片、Agent 输出三类绘制函数及像素文字排版。
- `task-displays.js`：把状态、场景注册表和 UI 串起来的共享控制器。
- `display-focus.js`：面板镜头计算与状态恢复。
- `agent-menu.js`：头像菜单、焦点管理与显示器聚焦入口。

各 `createOffice` 保留原返回字段，新增 `displays` 注册表，每项包含稳定 ID、类型、显示平面 Mesh、尺寸、工位/房间绑定及可选镜头覆盖参数。方向和位置从世界矩阵获取，支持父组旋转。

各场景入口挂接同一控制器，传入 camera、controls、actors、layout、displays 及生命周期钩子。本期不强制把全部旧入口迁移到 `bootScene`，避免将新功能与整套场景引擎重构混在一起。

显示资源、订阅和 mock 时钟在页面卸载及 HMR 时全部释放；约定清楚纹理/材质由哪个模块释放，避免新旧销毁逻辑重复释放或遗漏。

## 7. 分阶段实施顺序

1. **确定显示绑定**：复查五种布局的主板、白板、工位与遮挡；定义显示注册表、Agent 映射和数据协议。若缺主板则在现有可读位置扩展/补充。
2. **实现运行状态与 mock**：纯数据模块先跑通开始、分解、并行运行、受阻恢复、完成、重播；补充关键状态与时钟测试。
3. **打通 Loft**：采用现有长白板与电脑，完成主板、白板、至少两台独立电脑随同一时间轴更新；验证中文像素文字与材质独立性。
4. **完成聚焦与菜单**：主板/看板按钮、头像菜单、电脑特写、全景恢复；核验正反面、缩放上限和遮挡。
5. **适配其余四种布局**：补齐三人/九人、Suite、Floor 的注册与入口挂接；Floor 覆盖 24 台电脑及多房间看板筛选。
6. **完成回归与文档**：全部独立构建、行为测试、实际渲染截图检查；更新 README 的演示入口、操作方式、数据结构与后端替换说明。

## 8. 验收标准

- 五种布局中，都能在真实场景内的板面/屏幕上看到任务内容；DOM 浮层只能作为操作控件，不能代替场景显示。
- 同一轮演示的主任务、子任务、负责人和电脑日志一致，至少两个电脑同时显示不同输出。
- 能观察到等待 → 运行 → 受阻/恢复 → 完成；暂停和重播行为正确，没有旧日志残留。
- 每个头像菜单都能聚焦正确的固定工位电脑，包含 Floor 的 24 个角色；人物离开座位后仍正确。
- 聚焦时能直接读清中文，不出现字体缺字、文本穿框、背面镜头或永久遮挡；超长内容及超量子任务可翻页。
- 桌面、窄屏、embed、日间/夜间及减少动态效果下可用；低分辨率像素模式也需验证可读性，必要时特写期间临时提高渲染分辨率并在退出后恢复。
- 只重绘发生变化的显示面；纹理数不随演示时长持续增加；Floor 多次暂停/重播无明显卡顿或持续增长的资源占用。
- 原有动作、表情、寻路、人物选择、镜头预设及同源 embed 命令通过回归。

验证建议：

- 沿用 `node --test`，覆盖事件归并、乱序/重复事件处理、日志容量、演示时钟、重播、映射和分页等真实风险。
- 新增浏览器检查，读取可观测的运行状态并检查实际 Canvas 更新；通过截图核验字体、遮挡与对齐，不以仅断言 DOM 文本存在作为通过依据。
- 复用现有浏览器检查脚本，覆盖所有布局，并记录现有基线失败与新增问题。
- 在示例目录执行 `npm run test --workspaces=false`、`npm run build --workspaces=false`；另外分别用 `vite.loft.config.js`、`vite.suite.config.js`、`vite.floor.config.js` 验证独立构建。检查生产构建中的字体 URL 与资源加载。
